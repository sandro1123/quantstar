## 1. 系统总体架构与设计哲学

QuantStar 的核心目标是把量化交易从“脆弱的本地实验脚本”改造为“工业级可审计的生产系统”。框架严格贯彻以下五大不可违背的底层设计宪法：

### 1.1 核心设计宪法

1. **诚实降级，绝不静默 (Honest Degradation)**：
   任何数据缺失、超时截断或组件异常必须打上显式机器可读标记（如 `degraded_fallback=True`、`data_quality.valid=False`），严禁用伪造数据、历史均值或零值冒充正常。系统故障与业务低置信度必须严格分流。
2. **点截面对齐，防前视偏差 (Point-In-Time, PIT)**：
   历史数据仅可包含在计算时点当时已知的信息。财报数据严格绑定实际公告时点（`announced_at`）而非财务报表所属期（如 03-31），从物理上消除未来函数。
3. **建了必须通电 (Wired and Powered)**：
   编写功能代码、创建数据表必须同时具备真实调用点、调度排程入口和落痕存储。杜绝“写了代码没人调、建了配置没人读”的假接线。
4. **判据必须证明自己会红 (Falsifiability / Mutation Testing)**：
   任何业务监控与自动化守卫测试，在实现前必须证明当缺陷发生时能当场报红。无法捕捉真实故障的断言等于不存在。
5. **单点必有对冲 (Redundancy & Diversity)**：
   核心外部依赖（行情源、LLM 推理网关）必须具备同构备链与自动熔断降级通路，单一供应商波动不影响全盘运转。

## 2. 十层正典体系与层间契约

系统在物理目录结构和逻辑依赖关系上严格划分为十个层级，禁止同级双向依赖或反向跨层依赖：

```
                              ┌──────────────────────────────────────────────┐
                              │             Memory Layer (第十层)            │
                              │           系统长效记忆与生产事故判例库           │
                              └──────────────────────────────────────────────┘
                                                     │
    ┌─────────────┐    ┌─────────────┐    ┌──────────▼──┐    ┌─────────────┐    ┌─────────────┐
    │  01. Data   │───▶│02. Strategy │───▶│  03. Agent  │───▶│04. Execution│───▶│ 06. Report  │
    │  数据采集层 │    │   策略打分层 │    │  智能体辩论层 │    │  执行状态机  │    │   报告组装层 │
    └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘    └──────┬──────┘
           ▲                                                        ▲                  │
           │                                                        │                  ▼
    ┌──────┴──────┐                                           ┌─────┴───────┐   ┌─────────────┐
    │05. Backtest │                                           │   08. Ops   │◀──│07. Delivery │
    │  回测归因层 │                                           │  运维可观测层 │   │   多端投递层 │
    └─────────────┘                                           └─────────────┘   └─────────────┘
                                      ┌──────────────┐
                                      │  09. Config  │  全局配置与校验层
                                      └──────────────┘
```

### 2.1 各层职责与核心数据契约

| 层级编号 | 模块路径 | 核心入参 (Input Contract) | 核心产出 (Output Contract) |
|---|---|---|---|
| **01. Data** | `src/data_layer` | 标的代码、时间区间、数据类型 | 规范化 `KlineBar`、`FinancialSheet`、`MoneyflowData` |
| **02. Strategy** | `src/strategy_layer` | 规范化历史行情、财报数据截面 | 因子评分矩阵、中性化打分、`CandidatePool` (候选股票集) |
| **03. Agent** | `src/agent_layer` | 候选标的画像、宏观盘面、相关新闻 | 结构化 `AgentReviewResult` (多空观点、置信度、风险项) |
| **04. Execution** | `src/execution_layer` | `PlanProposal` (审核通过的买卖计划) | `StockPoolRow` (推荐池状态机单据)、`ActionRecord` |
| **05. Backtest** | `src/backtest_layer` | 标的历史行为序列、策略配置 | `BacktestMetrics` (夏普比率、最大回撤、超额收益) |
| **06. Report** | `src/report_layer` | 选股状态机快照、宏观情绪、交易流水 | `Message` 载荷 (富文本交互卡片、纯文本、摘要) |
| **07. Delivery** | `src/delivery_layer` | `Message` 对象、路由策略与渠道配置 | 消息投递收据、外部消息 ID（用于支持卡片就地更新） |
| **08. Ops** | `src/ops_layer` | 调度计划、交易日历、心跳与告警事件 | `PipelineRunRecord`、自动解死锁动作、运维日报 |
| **09. Config** | `src/config_layer` | 本地配置文件、环境变量、命令行覆盖 | 类型安全的 `ConfigRegistry` 单例、动态生效参数 |
| **10. Memory** | `src/memory_layer` | 生产异常特征、历史回测失败案例 | 决策增强上下文、自愈规则集 |

## 3. 多源异构数据流与 PIT 防未来机制

数据层是量化系统的地基，QuantStar 构建了业内领先的**多源熔断分族调度网络**：

```
                    ┌────────────────────────────────────────────────┐
                    │               Data Layer 统一路由器             │
                    └────────────────────────────────────────────────┘
                                            │
                     ┌──────────────────────┼──────────────────────┐
                     ▼                      ▼                      ▼
              ┌──────────────┐       ┌──────────────┐       ┌──────────────┐
              │ AkShare Sina │       │   Baostock   │       │   Tushare    │
              │  (快照/全量)  │       │  (历史逐股)   │       │ (财务/资金流) │
              └──────────────┘       └──────────────┘       └──────────────┘
                     │                      │                      │
                     └──────────────────────┼──────────────────────┘
                                            ▼
                                  ┌───────────────────┐
                                  │   数据清洗与三态判别 │
                                  │  - 空数据三态分流  │
                                  │  - 停牌行 NULL 记账│
                                  │  - 价格口径对调校验│
                                  └───────────────────┘
```

### 3.1 停牌日与价格污染防御 (F-23 判例)
在 A 股生产数据中，部分行情源对停牌股票可能返回 `close = 0.0`。
- **旧做法陷阱**：管道直接将 0 写入数据库，下游收益率计算得出 `-100%` 跌停假象，诱发整个投资组合净值瞬崩，进而触发虚假的“全组合熔断”；
- **QuantStar 工业级防御**：
  - **源层拦截**：`close <= 0` 且无有效撮合时，源适配器直接抛弃退化行；
  - **管道层保全**：停牌日价格自动重置为 `pre_close`，涨跌幅记录为 `change_pct = NULL`（不可算），严格保护前收盘价不被污染。

### 3.2 财务数据时点准确性 (Point-In-Time)
- 财报数据严禁按季度截止日（如 6 月 30 日）生效，必须按照上市公司在巨潮资讯等官方渠道的真实披露时间（`announced_at`）生效；
- 避免策略在 7 月初就使用尚未发布的半年报指标进行“完美选股”。

## 4. 因子引擎与截面评分流水线

### 4.1 因子接口抽象 (`BaseFactor`)
所有因子必须继承统一抽象基类，并实现纯函数式的计算逻辑：

```python
from strategy_layer.factors.base import BaseFactor, FactorContext, FactorResult

class CustomFactor(BaseFactor):
    name: str = "custom_factor"
    category: str = "momentum"  # momentum / value / quality / volatility
    window_size: int = 20

    def compute(self, ctx: FactorContext) -> FactorResult:
        # ctx 包含严格按时点隔离的 K 线与财务历史
        ...
```

### 4.2 截面清洗与正交化处理
因子计算完毕后，并不直接打分，而是经过四重标准化漏斗：
1. **缺失值处理**：数据行不足最小窗口的因子值赋值为 `None`，不参与截面排序；
2. **MAD 绝对中位数去极值**：
   $$\text{Median} = \text{median}(X), \quad \text{MAD} = \text{median}(|X - \text{Median}|)$$
   将极端异常值裁剪至 $[\text{Median} - 3 \times 1.4826 \times \text{MAD}, \text{Median} + 3 \times 1.4826 \times \text{MAD}]$；
3. **行业与市值中性化 (Neutralization)**：通过截面 OLS 回归剥离行业哑变量与对数市值因子敞口，提炼纯 Alpha 收益；
4. **Z-Score 标准化**：将因子得分归一化至均值为 0、方差为 1 的标准正态分布。

## 5. 多智能体 (Multi-Agent) 辩论与决策网络

### 5.1 辩论模型网络拓扑
QuantStar 在传统多因子初筛后，引入 LLM Agent 进行深度上下文质检：

```

                    │          候选股票画像 (池规模 TOP 10~20)        │
                    └──────────────────────────────────────────────┘
                                           │
                    ┌──────────────────────┴──────────────────────┐
                    ▼                                             ▼
          ┌────────────────────┐                        ┌────────────────────┐
          │ 多头分析师 (Bull)  │                        │ 空头风控官 (Bear)  │
          │ 挖掘成长驱动与催化剂│                        │ 寻找估值陷阱与潜在雷│
          └────────────────────┘                        └────────────────────┘
                    │                                             │
                    └──────────────────────┬──────────────────────┘
                                           ▼
                                ┌─────────────────────┐
                                │  中立裁决官 (Judge) │
                                │ 综合多空论据做出裁决 │
                                └─────────────────────┘
                                           │
                                           ▼
                                ┌─────────────────────┐
                                │ AgentReviewResult   │
                                │ (置信度 / 综合评语)  │
                                └─────────────────────┘
```

### 5.2 推理模型 Token 预算隔离 (`reasoning_floor` 护城河)
在接入 DeepSeek-R1、Kimi、hy3 等新一代推理大模型时，模型会先在内部输出大量思维链（Chain-of-Thought, CoT）。
- **行业通病**：传统客户端只设定通用 `max_tokens=2000`，导致推理模型在思考阶段就耗尽了 2000 tokens，回答正文为 0 字符（`content=""`），触发虚假报错；
- **QuantStar 架构创新**：在 Provider 配置层引入 `reasoning_floor` 动态下限垫底机制（默认 6000~8000 tokens）。调用方若传入小预算，底层自动抬升至充足的安全水位，彻底根除模型思考假死。

## 6. 标的全生命周期状态机与入池三闸

标的从被发现到最终清仓退出，由 `execution_layer` 严格按照状态机流转：

```
     [初筛候选]
         │
         ▼
     ┌───────┐      三闸检验通过      ┌───────────────┐      实盘/模拟撮合成交     ┌────────┐
     │ Watch │ ─────────────────────▶ │ Pending Entry │ ───────────────────────▶ │ Active │
     └───────┘                        └───────────────┘                          └────────┘
         │                                    │                                      │
         │ 超期未动                            │ 价格漂移/撤单                         │ 触发止盈/止损/离场
         ▼                                    ▼                                      ▼
     [已淘汰]                             [取消入场]                           ┌──────────────┐
                                                                               │ Exit Pending │
                                                                               └──────────────┘
                                                                                     │ 收盘对账结算
                                                                                     ▼
                                                                                ┌────────┐
                                                                                │ Exited │
                                                                                └────────┘
```

### 6.1 入池三闸防御体系 (Three-Gate Protection)
所有通过 Agent 审核的买入申请，在进入 `Pending Entry` 前必须顺序通过三道硬闸门：
1. **闸 A：时效闸 (Approval Age Gate)**：
   审批单的生成日期距离当前交易日不得超过 `approval_max_age_days`（缺省 2 个交易日），杜绝将多日前已失效的停牌或滞留单误入场；
2. **闸 B：价格现实闸 (Price Reality Gate)**：
   根据实时行情核验标的价格。若现价已跌破建议止损位（开仓即止损）或涨出入场价格上限（追高破坏策略赔率），当场拦截拒绝；
3. **闸 C：风险收益比守卫 (Risk-Reward Gate)**：
   计算理论赔率：
   $$\text{RR Ratio} = \frac{\text{Take Profit} - \text{Entry Mid}}{\text{Entry Mid} - \text{Stop Loss}}$$
   若 $\text{RR Ratio} < 1.45$，则认定为赔率不足的平庸机会，强制打回留痕。

## 7. 回测引擎与自适应参数演化 (WFO)

回测层为策略提供无前视、抗过拟合的真实环境检验：
- **Purged Cross-Validation (清除交叉验证)**：对前后时间重叠的交易样本进行强制隔离，消除自相关性与信息穿透；
- **Walk-Forward Optimization (步进前向回测)**：
  - 滚动滑动窗口：在 $T_{\text{train}}$ 窗口上优化因子组合权重，在 $T_{\text{test}}$ 样本外窗口验证真实 OOS 收益；
  - 杜绝静态拟合全历史导致的“幸存者偏差”。
- **全费率模型**：精确计提印花税（千分之一单向）、券商佣金（万分之 2.5，五元起投）与过户费，回测净值高度对齐实盘账户账本。

## 8. 生产调度、并发锁与自愈可观测性

### 8.1 交易日历调度与文件锁隔离 (`flock_guard`)
- 量化系统的最大痛点之一是由于多进程调度引发的 SQLite 读写锁竞争（`database is locked`）；
- QuantStar 通过 POSIX 文件锁 `flock_guard.sh` 实行严格排队机制。同一时刻只允许一个写入类管道独占数据库写连接；
- 结合系统级超时看门狗 `cron_watchdog.sh`，当任何管道因网络卡死超出预算时，优雅记录上下文并释放进程锁，确保整条调度链不会挂死。

### 8.2 结构化可观测追踪
系统内每个操作都具有全局唯一的 `trace_id`，并记录在统一运维表中：
- **`pipeline_runs`**：记录执行状态、持续时间、真实生效配置哈希；
- **`alerts`**：统一告警状态机（`open` ➔ `acknowledged` ➔ `resolved`）；
- **`action_records`**：标的每一笔状态变更与风控拦截的明确文本依据。
