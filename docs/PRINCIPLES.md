## 原则一：判据必须严格区分“坏了”和“没有”（三态律）

### 🚨 真实事故（F-22 族事故）
在执行层健康面检查中，曾有一个辅助函数 `_leg_health_face()` 永远返回 `{}`。
下游消费方读到空字典，判断为“今日数据尚未就绪”，因而静默标记缺失——**整整 23 天，53 只跟踪标的天天在报告中显示健康数据缺失，监控没有报出一声警报**。
所有人误以为是上游源头没给数据，而真相是：**该函数在代码重构后从未真正实现过**。

### 💡 核心原则
在分布式与量化流水线中，返回值为空绝不能简单用 `None` 或 `0` 一概而论，必须严格划分**三态**：

| 状态标识 | 语义定义 | 期望行为 |
|---|---|---|
| **`NONE`** | 我查不到 / 查询根本没有执行 | **系统故障态**：必须显式抛出告警或留下降级追踪 |
| **`EMPTY`** | 我查到了，但客观事实就是没有数据 | **正常业务态**：允许放行，但必须有显式日志留痕 |
| **`ERROR`** | 数据接口崩溃 / 驱动报错 | **系统异常态**：立即阻断，触发熔断与备链切换 |

**混同它们的后果是双向造假**：
- 把“查不到”当“没数据” ➔ 故障被彻底掩盖（如上文 23 天失明）；
- 把“没数据”当“故障” ➔ 在节假日或无交易时段制造成千上万条狼来了式的假告警。

## 原则二：守卫必须先证明自己会红（反向变异测试）

### 🚨 真实事故（G3 与 150 巡检）
在一次针对报告层超时预算的重构中，开发席位引入了新的 `@with_timeout` 装饰器，并配备了 15 个自动化测试，测试在本地与 CI 上全部全绿。
然而在后续全链路审计中，审计官将核心的执行语句 `msg = builder.build()` 故意注释掉，**这 15 个测试居然依然全绿**！
原因在于：测试内部为了隔离外部依赖，直接 mock 掉了顶层方法，测试断言的全是 mock 行为，根本没有触碰被测业务的核心分支。

### 💡 核心原则
**没有经过反向变异验证（Mutation Testing）的测试，不是测试，是在测空气。**
- 编写任何守卫测试（Nail/Guard）时，必须故意打断真实接线（如将配置从 180 改为 120，或删除关键字段）；
- **守卫必须当场报红（RED）**，且报错信息必须精准指明缺陷点；
- 只有亲眼看到守卫会咬人，恢复接线后获得的绿色（GREEN）才具备真正的工程信任度。

## 原则三：降级必须有名有姓，禁止假绿冒充

### 🚨 真实事故（F-21 降级覆盖漏洞）
在大模型分析链路中，当底层 LLM 发生网络抖动或超时，规则引擎会自动触发降级，生成一个默认置信度（`confidence = 0.30`）。
而策略初筛逻辑中恰好有一行风控硬闸：`if confidence <= 0.30: drop()`。
导致的结果是：系统一旦遭遇网络断供，所有优质股票都被规则引擎判定为“低置信度垃圾标的”而全盘剔除，推荐池瞬时归零。运维人员在排障时误以为“今天市场上确实没有好股票”。

### 💡 核心原则
- **故障降级与业务判断必须严格隔离**：
  降级分支产出的对象必须显式携带 `degraded_fallback = True` 标识，并在报告和界面上清晰标注“系统网络降级，暂无 AI 观点”；
- 绝不允许用看起来合法的“业务中性值（如 0 分、0.3 分、50%）”静默填补系统崩溃，这是最危险的虚假繁荣。

## 原则四：生产与消费的键名契约必须对齐

### 🚨 真实事故（G7 WFO 键名不对齐）
在 Walk-Forward 回测优化中，前向计算模块 `walk_forward.py` 计算出样本外表现，写入结果字典：
`result["oos_efficiency"] = 0.82`。
然而持久化存储模块 `persistence.py` 却写成了：
`efficiency = result.get("efficiency")`（遗漏了 `oos_` 前缀）。
读取结果永远是 `None`，导致数据库中全写成了 `NULL`。系统因此判定所有策略参数效率不合格，步进优化门禁永久亮红灯。更讽刺的是，两边各自的单元测试由于都基于本地假数据构造，测试全部绿灯通过。

### 💡 核心原则
- **测试必须跨越对象边界**：单测不能只测“函数自己能不能跑”，必须有契约测试验证“生产者产出的真实 Key，消费者能原封不动解析”；
- 杜绝散落在代码各处的魔术字符串（Magic String），跨模块共享的字典键名与参数必须以显式常量或强类型 Schema（如 Pydantic / TypedDict）统一管理。

## 原则五：分类问题常是伪装成分类的同一个错误

### 🚨 真实事故（F-23 停牌 79 行定谳）
数据表中出现了一批收益率为 `-100%` 的股票。
初期的分析报告将其分为两类问题分别排查：“类型 A（部分股票已复牌但报错）”、“类型 B（部分股票未复牌依然停牌）”，甚至准备为两类编写不同的修复补丁。
最终逐行代码溯源发现，根本不存在两种情况——**全因行情源在停牌日直写了 `close = 0.0`，管道层将其与前收盘价相除，算出了 `(0 - pre_close) / pre_close = -100%`**。
所谓的“类型 A 与 B”，仅仅是有的股票后来复牌被新数据掩盖，有的股票还没复牌暴露在外而已。

### 💡 核心原则
当发现系统出现多种看似不同的异常形态时，不要急于为每种形态打“补丁”或“分类处理”，务必沿数据流向顺藤摸瓜找到最初的那个**单点根因（Single Root Cause）**。在源头斩断污染，下游看似复杂的所有表象会瞬间不攻自破。

## 原则六：写钉的人也要守钉（守卫自噬定理）

### 🚨 真实事故（C 卡一致性守卫反噬）
在开发配置一致性守卫时，我们制定了严格规则：“任何未在 `ops.yaml` 声明独立管道的方法，禁止带 `config_key` 参数；若带有，必须在源码注释中显式写明理由 `无独立管道宿主`”。
然而在提交的第一版代码中，开发工程师写的是 `本方法不经调度直接运行`。
测试套件在执行时当场报红：**守卫毫不留情地拦截了守卫作者自己编写的代码**，直到注释规范化为约定术语。

### 💡 核心原则
- 自动化规则与代码门禁必须是**无情的冷血机器**，对所有人一视同仁；
- “写规则的人当场被规则咬一口”，恰恰证明了该防线真正具备物理拦截效力，而不是写给领导看的虚晃一枪。

## 原则七：超时重试取决于故障性质，拒绝盲目放大

### 🚨 真实事故（晚报重试雪崩）
晚报生成由于包含复杂的多因子汇总与大模型生成，单次运行通常需要 40~60 秒。在某次模型服务器网络拥塞时，晚报超过 120 秒超时。
调度器配置了 `max_retries = 2`。结果调度器当场重试了 2 次，总耗时暴涨到 360 秒（6 分钟），不仅没有成功，反而连续霸占数据库写连接，导致盘后的数据备份与清理任务全部被锁饿死。

### 💡 核心原则
- **超时（Timeout）与瞬时错误（Network Flake）具备完全不同的物理性质**：
  - 网络丢包、连接被重置适合快速指数退避重试；
  - 运算超时往往意味着**当前计算复杂度超标、资源严重拥塞或存在隐式死锁**，盲目重新来过只会成倍浪费算力并放大级联雪崩；
- 复杂报告与密集批处理管道，超时的正确处理姿态是**“当场死透并留下上下文”**，由监控报警唤醒工程师或自动排错，而不是在生产环境反复空转。

## 原则八：给推理模型以思考的尊严（Token 预算隔离）

### 🚨 真实事故（G9 推理模型假死）
在引入具备深度推理能力的大模型（如 DeepSeek-R1、hy3）后，晚报连续三天超时失败。
日志显示，调用时传入了标准的 `max_tokens = 2000`。模型在生成回答正文前，输出了 2,857 字的深度思考过程（Chain-of-Thought）。2,000 个 token 在思考尚未结束时便全部耗尽，返回报文中的回答正文长度为 0，HTTP 状态码却依然是正常的 200。系统解析不到文字，判定为大模型接口故障。

### 💡 核心原则
- 新一代具备思维链的大模型，其 Token 预算消耗模型已发生根本变化：同一个参数，在传统模型上是“输出长度”，在思考模型上是**“思考 + 回答的总预算”**；
- 架构必须在网关层抽象出 **`reasoning_floor`（推理底线预算）** 机制。面对具备推理属性的模型，底层统一将调用预算抬升至充足的水位（如 6,000~8,000 tokens），给模型完整的思考空间，彻底避免被截断带来的假死。
